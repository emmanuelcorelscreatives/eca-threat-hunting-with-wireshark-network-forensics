# Synthetic data dictionary and implementation contract

All rows are **authored scenario design or metadata**, not packet-derived observations. `scenario-plan.csv` is **not** the supplied builder’s version-1 JSON event schema. Its `event_id` is a plan ID, never a frame number. `time_utc` and both context windows use ISO 8601 UTC. Empty `ip_src`/`ip_dst` on ARP means there is no IPv4 header; ARP’s `spa`/`tpa` are different fields. The two `trace_id` values describe independent examples.

`scenario-plan.csv` columns: `trace_id`, `event_id`, `time_utc`, `protocol`, `ether_src`, `ether_dst`, `ip_src`, `ip_dst`, `fields`. The final column is semicolon-separated `key=value` design data; `udp` gives source-to-destination ports. Ethernet/ARP/DHCP hardware aliases: `C=02:00:00:00:00:44`, `S=02:00:00:00:00:02`, `G=02:00:00:00:00:01`, `F=02:00:00:00:00:50`, `P=02:00:00:00:00:60`, `Q=02:00:00:00:00:61`, `R=02:00:00:00:10:01` (server-side next hop), `V=02:00:00:00:10:02` (server), `B=ff:ff:ff:ff:ff:ff`, `Z=00:00:00:00:00:00`, `M=01:00:5e:00:00:fb`. Aliases name authored roles, not actual devices.

ARP: `op=1` request or `op=2` reply; `sha`/`spa` are sender hardware/IPv4, `tha`/`tpa` target hardware/IPv4. DHCP: `chaddr` is BOOTP client hardware, independent of Ethernet source; `ci`, `yi`, `gi` are BOOTP client, offered/client-address and relay-agent addresses. `server` is DHCP server identifier, **not necessarily** the IP source. `requested` is an option; its absence during renewal is intentional. `lease` is seconds. `0.0.0.0` in DHCP/ARP fields and DHCP broadcast destinations are required protocol values, not documentation-network hosts. On the bidirectional server-link trace, Ethernet source `R` is an immediate hop, while DHCP `chaddr` identifies the independent client.

Discovery: `qclass=IN+QU` requests a unicast answer; `qr` distinguishes query/response; `answer` is a proposed A-record address; `payloadDecimalOctets` specifies deliberately too-short DNS content. Actual TShark4.2.2 dissection is supplied; native GUI execution is not claimed.

`capture-context.csv` fields are trace ID, *proposed* capture point, authored window, visibility scope, known gaps and synthetic status. They do not certify collection quality. `dhcp-binding-record.csv` is one synthetic server-record scenario row keyed by MAC, address, server and transaction ID; `event_type=ACK-record` is not a packet or evidence of later use. It has no operator, authorization or process field.

**Implemented offline builder:** generate_fixture.py reads this exact CSV and emits both descriptive PCAP filenames with fixed UTC microsecond timestamps. verify_fixture.py uses independent TShark dissection and checks all plan fields, frame times, pivots, checksums, binding join, regeneration and overwrite refusal. No Scapy or Python package dependency is required. printer.local is an authored supplemental example, not a saved-lecture example. The supplied decoder CSVs are packet-derived observations of synthetic files; scenario and binding CSVs remain authored metadata.
