The included `practice.pcap` has SHA-256 `610fd5d81606704845f97400c085fe49bba38be534111694998521159ec58a97` and is 498 bytes. Actual TShark 4.4.0 execution selected original frames **2, 4, 6** for `tcp`, with three filtered summary rows and six unfiltered summary rows. Native Wireshark 4.4.0 opened the same bytes through File > Open with no read filter: six total packets, three displayed, ordered No. 2, 4, 6. See the two packet-list screenshots, command stdout and execution proofs. These were Linux runs, not Windows runs. A deterministic rebuild matched every capture byte.

UDP frames are 1, 3, 5. TCP frame 2 is SYN from `192.0.2.10:51000` to `198.51.100.20:41000`, raw sequence 1000 and raw acknowledgment 0. Frame 4 is reverse SYN/ACK, raw sequence 7000 and acknowledgment 1001. Frame 6 is ACK, raw sequence 1001 and acknowledgment 7001. The GUI uses relative sequence numbers by default: respectively Seq=0, Seq=0 Ack=1, Seq=1 Ack=1 in these screenshots. These are consistent representations, not different selections. Raw field values are in `tcp-details.stdout.txt`.

A satisfactory comparison records the unchanged file identity, empty opening read filter, identical display expression, actual counts **and** ordered original frame numbers. Gaps in the filtered No. column hide captured nonmatches, not missing packets. Different summary columns alone do not establish different selections. A different working copy has no predetermined answer; zero matches supports only a claim about that file and filter. TCP decoding does not establish authorization, application identity, purpose, completeness or a threat. This invented handshake carries no application payload. Do not infer historical case findings from it.

If observations differ, check file paths and hashes, the opening read filter, the display expression and relevant installed-tool analysis settings.
