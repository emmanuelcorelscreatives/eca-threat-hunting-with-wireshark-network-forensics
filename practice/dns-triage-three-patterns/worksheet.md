# Exercise: compare three explanations

Use `scenario-cards.csv` first as an explicitly invented, **non-packet** exercise. Its seconds are modeled offsets, not capture timestamps. State a hypothesis for D (discovery), F (application failure) and U (unexplained queries). Compare questions, response states and spacing. For D, ask whether the PTR instance connects to its SRV and TXT questions and whether an approved service and asset role are independently confirmed. For F, distinguish an NXDOMAIN response from no visible response; ask for an application or owner record matching the window. For U, consider varied names, visible answers, possible later traffic and ordinary application explanations. A name's appearance and packet count prove neither legitimacy nor compromise.

For each candidate, write three separate sentences: **observed** (only if cited from an identified capture or record), **inferred** (an explanation), and **unknown** (what the available sources cannot settle). The scenario cards provide modeled facts, not observations. State a conditional first follow-up and the checks it depends on; then state whether the actual saved case can be ranked.

For the supplied synthetic practice.pcap, use `dns-triage-worksheet.csv` for **one row per transaction**, adding rows as needed. Cite source filename, original query and response frames, displayed time, visible source, name/type, result and answer. Leave unsupported fields blank; a missing response is not NXDOMAIN. Record later traffic with its own frame and time, not as proof of a process or purpose. Note whether the capture is client-to-resolver, resolver-to-outside, or both: an outward source may be a shared resolver, and cache hits may leave no outward query. Check whether a short window, translation, shared hosting or encrypted DNS could limit the comparison.

Choose a narrow next request: service-owner confirmation for D, application or endpoint context for F, or resolver/client mapping when outward packets cannot identify U's requester. If evidence cannot separate the candidates, say **inconclusive**. This DNS triage prepares for the next lesson, “Read HTTP Requests and Responses as a Sequence”; it does not analyze HTTP here.
