# Worksheet

Question: did an unexpected machine answer a name request during the recorded period, and what did the client visibly do next?

1. Record the practice filename, SHA-256, synthetic provenance, UTC window, constructed observation point and assumed subnet. Separate those scenario assumptions from decoded packet facts. State why this is not the missing historical incident or an actual collection-completeness claim.
2. Apply `udp.port == 5355`. Expand LLMNR details. Record request frame, requester, numeric multicast destination, queried name and transaction ID. Match both replies using name, ID, direction and time. Keep each reply source separate from its returned address. Compare both with asset-map.csv. Explain a benign alternative for multiple replies.
3. Apply `nbns`. Compare the broadcast request with the configured-server request. Record request/reply frame pairs, IDs, NetBIOS name and suffix, destinations, response sources and returned IPv4 addresses. State the subnet assumption that makes the first request a broadcast. Explain why the configured NBNS server need not own the returned file-server address.
4. Apply `dns && (udp.port == 53 || tcp.port == 53)`. Record question, intended resolver, transaction ID, response flags, both reply sources and answers. Check any linked request frame supplied by Wireshark; do not manufacture a link when absent. Does the unusual response source by itself establish a valid client DNS match or spoofing? Explain source-port and resolver expectations.
5. Remove the name-resolution filter, then use `tcp`. Record first SYN, SYN/ACK and ACK frames, endpoints, timing relative to the DNS answers, and whether application payload appears. Distinguish reply observed, connection observed, authentication material observed, and credentials captured by someone. Which claims are supported? Which causal claim about address choice remains unproved?
6. Write an analyst note another person can retrace: file/window/filter/frame pairs, source versus answer address, expected asset role, competing explanations, confidence and next action. Include resolver/NBNS configuration, owner and approved-change checks. Explain why absence in a real short or one-sided capture cannot prove the client never connected.
