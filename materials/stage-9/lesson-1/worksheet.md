# Follow a complete DNS transaction

**Question:** Does a query leaving a recursive resolver identify the workstation that wanted the name? No: first establish the capture point, follow one visible question **and** reply, and name only the requester evidenced on that link. Use the unchanged `dns-transaction-worksheet.csv` for separate client-facing and upstream rows. The packaged four-frame capture makes these pairs available, but its link roles are authored synthetic notes, not historical sensor evidence. Its current command logs do not replace the required DNS-detail and Wireshark inspection.

1. **Establish scope before filtering.** Record your actual approved offline source file or documented working copy, collection notes, UTC window, link(s), and possible missed directions or segments. For `practice.pcap`, read `collection-notes.md`: a stitched two-link scenario cannot prove coverage by one physical collector. For your own authorized capture obtain its *own* collection notes. An empty view cannot prove that no lookup occurred.
2. **Choose and inspect a question.** Open the file with Wireshark **File → Open**, apply `dns`, and pick a query within the noted window. The filter changes only the displayed view. Record its actual frame/time, source and destination IP addresses, UDP or TCP transport ports, query flag, DNS transaction ID, and Question name, type and class from **Domain Name System**. An A question asks for an IPv4 record; AAAA asks for an IPv6 record. A visible attempt establishes neither a successful resolution nor a later connection. Do not infer a workstation from an IP address until you know which link is represented.
3. **Match the response, not merely an ID.** Follow Wireshark’s response-frame link **if present** and independently verify its actual frame/time, response flag, ID, same question, and addresses and ports reversed between the same participants. IDs may recur and missing packets can mislead. Check the response code and expand **Answers**. Transcribe only Answer-section names, types and values: A is an IPv4 address, AAAA an IPv6 address, and CNAME an alias pointing to another name, **not** an address. The Answer owner or type may differ from the question. Do not copy an Authority or Additional record, or a name displayed by Wireshark’s own IP name resolution, into `answer_records`. A reply with no usable address must be described as such.
4. **Record two separate pairs.** The executed fixture specification models a client-facing query/reply and a resolver-upstream query/reply. Use frame references established from the capture, not the specification’s list order alone. The current `all-frames.stdout.txt` reports names, A question types and `dns.a` values, but not ports, IDs, response flags, response code, Answer owners or TTL. The packaged builder predicts those remaining details; verify them in the packet details before calling a CSV row fully checked. If one direction is absent in another capture, mark its packet fields `not_visible` and the exchange incomplete; never supply an expected answer as an observation.
5. **Separate observation, link attribution and inference.** On a verified client-facing link, an endpoint asking its resolver is the *observed requester on that link*. On an upstream link the visible requester is the resolver; its packets alone do not identify an original endpoint. Shared names and near times are leads, not proof that one pair caused the other. An absent upstream query might be cache reuse **or** missed capture coverage; test with a contemporaneous client-side view, resolver request/cache records, and collection evidence. Say `unknown` if attribution remains unresolved. An answer address is a resolution lead, not proof of contact with that address, an application, or a user.
6. **Finish the lecture’s own-capture exercise.** Try one complete visible DNS transaction in your *own authorized offline capture* and report its actual capture, frames, question, ID, reversed addresses/ports, response code, **Answer** records and collection link. If only an upstream pair or a missing packet is available, give that qualified finding and request the client-side or resolver records needed to identify the endpoint. If you encounter AAAA, CNAME, no usable Answer, or failure, apply the same inspection method; this four-frame A-only fixture does not supply those examples. The next lesson, **Analyze Failures, Bursts and Repeated Lookups**, examines unsuccessful and repeated patterns beyond this transaction.
