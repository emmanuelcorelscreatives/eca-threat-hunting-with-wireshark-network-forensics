# Data dictionary

All names, addresses, accounts, records, and times are **synthetic teaching data**. IPv4 addresses use documentation networks. Spec files are version-1 inputs for the supplied offline builder; `events` are timestamp-ordered. Each TCP event has `timestamp` (UTC), `kind`, `src`, `dst`, `sport`, `dport`, `flags`, `seq`, and `ack`. Empty payload is intentional: the builder models TCP here, not remote-service authentication. SYN and FIN each advance the designed sequence by one. One spec represents one observation point; the builder writes classic PCAP, not the planned PCAPNG files.

`supporting-records.csv` columns: `record_id` is a unique citation; `kind` selects the row schema; `start_utc` and `end_utc` bound an assignment, plan, or collection statement (equal times denote a recorded event); `system` is the synthetic device or observation point; `ip` is its assigned or destination address; `peer_ip` is the recorded source or expected peer; `account` is a record value, **not verified ownership**; `outcome` is the row's stated status; `detail` qualifies it. Blank means **not supplied**, never a negative result.

Kinds: `assignment` gives historical address-to-device intervals; `auth` is an authored destination-log excerpt; `host` is an authored destination-activity excerpt; `admin-plan` is expected approved work; `coverage` and `gap` are **hypothetical scenario metadata**, not measured PCAP properties; `availability` describes missing excerpts, not absence of events; `roster` nominates a system without traffic evidence. CSV logs are not emitted or correlated by the packet builder. Match timestamps with clock uncertainty and require an actual session reference before treating nearby entries as the same session.
