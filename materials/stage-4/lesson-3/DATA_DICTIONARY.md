# Synthetic resource dictionary and evidence scope

**Status and provenance.** The assembled but unpublished kit contains the real `offline-builder.py`, `executed-fixture-spec.json`, its currently byte-identical alias `fixture-spec.json`, and `practice.pcap`. The executed spec is the **actual deterministic builder input**, SHA-256 `ac10acf238351b1242604f9d4e5d86f2df0a6ae853070185f1a83e4431558753`; use it if an alias ever differs. The packaged PCAP and identical local rebuild have SHA-256 `5a86a3faeee6761289d4f2ab75e11ddb01b83a1b26ce65d1969aa492985885f3`. The builder’s `--spec` and `--output` options read local data and write a PCAP; the current packaged version refuses an existing output. It does not send traffic or implement the earlier proposed `--verify` flag. The bounded native Linux GUI checks are now established in `native-validation.md`. A versioned public download and Windows checks remain unverified.

**Spec fields.** `version: 1` and `synthetic: true` mark the required format. `fixtureId`, `purpose`, `scope`, `observationPoint` and `sourceLessonProjects` document exercise intent; `observationPoint` is an authored link, **not** evidence of a physical collector or measured coverage. Ordered `events` have explicit UTC ISO-8601 `timestamp`, `kind`, documentation IPv4 `src` and `dst`, and transport ports `sport`/`dport`. `dns-query` and `dns-answer` use reserved `.test` `name` and matching `transactionId`; the answer includes IPv4 `answer`. `tcp` events provide `flags`, raw byte sequence `seq`, raw acknowledgment `ack` and optional literal `payloadText`. The authored HTTP text is harmless exercise content, not proof that a real process ran. The general builder permits other event kinds and optional capture truncation, but they are not present in this 13-event fixture. The spec’s flags describe design; the supplied all-frames TShark output exports raw sequence/acknowledgment fields, **not** `tcp.flags`.

**Capture and decoded-field meanings.** `practice.pcap` is an Ethernet pcap with 13 included packets across an authored 0.300000-second UTC span; `192.0.2.10` is the assumed candidate host, `192.0.2.53` a synthetic DNS peer, and `198.51.100.20` a synthetic service peer. These documentation addresses and `service.academy.test` do not establish public routing, real ownership or process identity. Executed `capinfos practice.pcap` reports 1,159 **file bytes** and 927 **packet-data bytes**. In `all-frames.stdout.txt`, `frame.number` is the source-file reference; `frame.time_utc` is a formatted UTC date/time such as `Apr  8, 2025 09:30:00.000000000 UTC`, **not ISO-8601**; `frame.time_epoch` is decimal Unix-epoch seconds. The pinned 4.4.0 field inventory does **not** support `frame.time_iso8601`. The PCAP stores microsecond timestamps even if the decoded display pads to nine fractional digits. `frame.len` is a whole-frame byte count, `frame.cap_len` the captured whole-frame byte count, `tcp.len` TCP payload bytes, `tcp.payload` payload hex, and `http.file_data` decoded response-content hex—not a whole frame or automatically a downloaded file. `tcp.seq_raw` and `tcp.ack_raw` are on-wire raw values, not necessarily Wireshark’s default relative-sequence display. `dns.qry.name`, `dns.qry.type`, `dns.a`, `http.request.method`, `http.request.uri`, `http.host` and `http.response.code` are decoded fields; cite the frame containing each observation. A response-frame request URI, if populated through dissector association, is not a URI transmitted in that response. Conversation and protocol-hierarchy byte totals count included frame bytes, not HTTP content bytes. Empty `malformed.stdout.txt` means the executed `_ws.malformed` filter selected no frames; it does not establish missing-traffic absence or intent. The supplied CLI logs come from read-only pinned TShark/capinfos 4.4.0 Linux execution. Separate actual native GUI evidence and its limits are documented in `native-validation.md`.

**Independent context.** `supplemental-context.csv` (exact filename) has one parsed synthetic scenario-calendar row. `record_id` is its local key; `record_type` identifies calendar metadata; `asset_id` and `asset_ipv4` associate a *scenario* asset and address; `possible_service` and `planned_peer_dns` express a benign hypothesis; `scheduled_start_utc` and `scheduled_end_utc` bound a **planned**, not observed, window; `record_status` states its execution status; `evidence_scope` lists facts it cannot establish. Row `CTX-01` names `LAB-WS-01`, `192.0.2.10`, `scheduled_software_status_check` and `service.academy.test`, with window `2025-04-08T09:25:00Z`–`2025-04-08T09:35:00Z`, status `planned_not_execution`, and scope `not_packet_or_process_or_owner_approval`. This CSV is **not** a host, process, identity or owner-approval log. Matching its time and name to packet fields does not join a packet to an initiating process or prove the plan ran.

The capture and calendar support a **synthetic practice question**, not a historical Project One finding. The narrated case still needs its own authorized capture, intake/coverage notes and relevant background records. Cleartext HTTP here allows a protocol-level T1071.001 question; neither it nor the calendar proves command-and-control or settles the ordinary-service alternative.
