## Repeat the timing workflow safely in Wireshark

Use a **working copy** of an authorized offline source and preserve its original. For this supplied fixture, a proposed read-only identity check before making or opening the copy is `sha256sum practice.pcap`; compare its output with the source SHA-256 above. This is a learner recipe, **not** a claim that this command was part of the recorded native run. Record in the submitted worksheet companion: **Original capture filename:** ______; **Original capture SHA-256:** ______; **Opened working-copy filename:** ______; **Opened working-copy SHA-256:** ______; **Scoped client IP:** ______; **Scoped peer IP:** ______; **Scoped peer TCP destination port:** ______; **Capture window and time zone:** ______; **Capture point and basis:** ______; **Collection, clock, direction, loss and mapping notes:** ______. Record the opened-copy SHA-256, compare it with the approved original SHA-256, and retain that comparison result. `DATA_DICTIONARY.md` specifies the companion recording location because the existing CSV has no dedicated hash or port columns.

1. Choose **File > Open**, select the authorized working copy and open it without an unintended read filter. Confirm the packet count and original frame numbers. For the packaged fixture only, read `scope-card.md` and check the Source, Destination and TCP destination port rather than assuming a shared peer makes sources comparable.
2. Type `tcp.flags.syn == 1 && tcp.flags.ack == 0` in the display-filter bar and apply it. For this fixture, narrow the candidates with `tcp.flags.syn == 1 && tcp.flags.ack == 0 && ip.src == 192.0.2.10 && ip.dst == 198.51.100.20 && tcp.dstport == 80`. Inspect nearby unfiltered packets, four-tuples, SYN flags, raw versus relative sequence numbers and `tcp.stream`. Exclude frame 4 as a retry; frames 1–2 do not disclose their connection start. Once decisions are recorded, use the **actually approved accepted-only** filter `frame.number == 3 || frame.number == 20 || frame.number == 24` to cross-check the connection series. A frame-number filter is a view of decisions, **not** a method for deciding them.
3. Start the **separate** request series with `http.request`, narrowed for this fixture to `http.request && ip.src == 192.0.2.10 && ip.dst == 198.51.100.20 && tcp.dstport == 80`. Select decoded frame 8 and inspect its TCP reassembly links, then inspect the captured bytes and TCP payload of original frames 7 and 8; inspect frame 12 separately. Record first observed request bytes consistently, not a convenient decode-completion timestamp. The approved accepted-only first-byte filter is `frame.number == 7 || frame.number == 12`. The bare `http.request` filter selects 8 and 12 and cannot by itself display the first-byte pair.
4. With **one accepted series at a time** displayed, choose **View > Time Display Format > Seconds Since 1970-01-01** in the tested native menu. The lecture calls this Seconds Since Epoch. Record each accepted row's original frame and epoch time; calculate each later `Δᵢ = tᵢ − tᵢ₋₁` yourself, leaving the first interval blank. If needed, choose **View > Time Display Format > UTC Date and Time of Day** to document the displayed UTC context. Preserve the source and time-zone context; extra displayed digits do not validate a collector clock.
5. For the display-only cross-check, choose **View > Time Display Format > Seconds Since Previous Displayed Packet**. Verify that each row immediately above a later accepted event is **another accepted start of the same type, client, peer and port**. Do **not** use Seconds Since Previous Captured Packet for this shortcut: its predecessor may be hidden by the filter. A displayed first-row `0.000000` is not a worksheet interval. Clear the filter when inspecting exclusions, and restore the accepted-only view only after confirming its exact rows.
