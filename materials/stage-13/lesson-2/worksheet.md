# Worksheet — Measure Inter-Arrival Timing

**Threat Hunting with Wireshark, Stage 13, Lesson 2. Instructor: EMMANUEL CORELS.** The lecture is unchanged. Ask whether one scoped client repeatedly starts the **same kind** of contact with the same peer, then measure gaps between confirmed starts—not gaps between nearby packets. A TCP connection attempt and a visible HTTP request start are different events. Timing alone does not identify a process, prove remote instructions or establish command and control.

## Select and document events in Wireshark

1. **Open and assess coverage.** Use **File > Open** to open the offline working copy, without a read filter. Check the original **No.**, Source, Destination and Time columns and the start and end of the capture. Record boundary conversations with no visible start, missing directions, possible dropped or truncated packets, and clock limits. If addresses changed or traffic was translated, obtain a defensible mapping before combining rows; a common destination is not enough. `native-00-file-open.png` shows a chooser before opening, while `native-01-unfiltered.png` shows this fixture open with 26 packets. Neither proves real-world coverage.
2. **Find connection-attempt candidates.** Enter `tcp.flags.syn == 1 && tcp.flags.ack == 0` in the display-filter bar and apply it. It selects SYN with ACK clear, not proof of an established connection or request. On this fixture, the reviewed `native-10-filter-01.png` shows frames 3, 4, 18, 19, 20 and 24. To narrow by this card's direction and port, apply `tcp.flags.syn == 1 && tcp.flags.ack == 0 && ip.src == 192.0.2.10 && ip.dst == 198.51.100.20 && tcp.dstport == 80`; check that the resulting scoped candidates are 3, 4, 20 and 24, as shown for those criteria in `native-scope-payload-01-scoped-syns.png`. On **your own capture**, substitute its documented scope, never these example addresses.
3. **Decide, rather than count the filtered rows.** For every candidate, inspect adjacent packets, direction, source and destination ports, SYN and ACK flags, `tcp.stream`, and raw sequence numbers where available. Wireshark may display relative sequence numbers; distinguish them from `tcp.seq_raw`. Record the original frame, `TCP connection attempt`, and `accepted`, `excluded` or `uncertain` with a packet-based reason. In the fixture, frame 4 has the same tuple, stream and raw SYN sequence as frame 3 and is the retry; frames 18 and 19 are outside the stated client or peer scope. Frames 3, 20 and 24 are separate observed starts. Frames 1 and 2 are a midstream ACK-only context, **not** a timed start. Later ACKs, responses, transport keep-alives if established, and closing packets are not new connection starts: the fixture's frames 15 and 16 are FIN/ACK closing traffic, and frame 23 is ACK-only, not an established keep-alive mechanism. If only one long-lived session is visible, report that there is no series of separate connection starts.
4. **Build a separate request-start series only when requests are visible.** Apply `http.request`, then narrow to the intended client, peer and port, for example `http.request && ip.src == 192.0.2.10 && ip.dst == 198.51.100.20 && tcp.dstport == 80` for this fixture. The reviewed `native-scope-payload-02-scoped-http-decode.png` shows decoded GET rows 8 and 12. Inspect each row's underlying TCP segments, packet bytes and reassembly links; clear or change the filter to inspect a linked earlier frame. Use the same rule for every retained request: timestamp its **first observed request bytes**, not automatically its HTTP decode or header-completion row. Here frame 7 carries the first 17 bytes of `GET /a`, at raw sequence 1001; frame 8 carries the next 25 bytes beginning at **1018 = 1001 + 17** and completes the 42-byte header at **1043 = 1018 + 25**. Frame 9 ACKs 1043. Frame 12 carries all 42 bytes of `GET /b` beginning at 1043, and frame 13 ACKs **1085 = 1043 + 42**. The approved frame-7, frame-8 and frame-12 payload-detail PNGs in `native-independent-approvals.json`, `all-frames.stdout.txt` and `independent-pcap-report.json` support those distinct byte origins. Record first-byte frames **7 and 12** for this fixture's request series; put decoded row 8 in frame 7's `reason`, not in a second start row. Both requests reuse stream 1. If an earlier request portion was not captured, mark its start uncertain and leave its exact start-time cell blank; a later decoded segment cannot supply a missing first-byte time.
5. **Fill the CSV without losing exclusions.** `DATA_DICTIONARY.md` defines the existing columns. For each retained event enter `source_capture`, original unfiltered frame number, scoped addresses and window, observed `tcp_stream`, event type, decimal epoch timestamp, `timestamp_rule`, `start_certainty`, status and reason. Include excluded or uncertain candidates and relevant non-start or missing-start context, with reasons; do not put an excluded or uncertain start into interval arithmetic. The CSV's `capture_point` is authored context for the synthetic source, not a conclusion from one packet. Keep the original hash and scoped destination port in the accompanying scope block above. Do not mix request starts with SYN attempts in one series.

## Measure and cross-check each series

- Sort accepted starts by time **within the same client, peer, port, event type and timestamp rule**. Use **View > Time Display Format > UTC Date and Time of Day** when checking UTC context. Then choose **View > Time Display Format > Seconds Since Epoch**; the reviewed Linux Wireshark menu calls this **Seconds Since 1970-01-01**. Confirm the selected radio item and read each retained frame's epoch-seconds Time value. The approved `native-accepted-3-epoch-menu.png`, `native-accepted-3-epoch-applied.png`, `native-accepted-4-epoch-menu.png` and `native-accepted-4-epoch-applied.png` show those exact checked menu states and applied rows. Keep the capture identity, UTC context and clock caveats with the numbers; six displayed decimal places do not prove clock accuracy.
- Leave `previous_accepted_frame` and `interval_seconds` blank for each series's first accepted start. For every later one, record its preceding accepted **same-series** frame and subtract epoch times: `Δᵢ = tᵢ − tᵢ₋₁`. For the synthetic connection series, `1737028860.100000 − 1737028800.100000 = 60.000000` seconds and `1737028920.100000 − 1737028860.100000 = 60.000000` seconds. For the separate request first-byte series, `1737028821.100000 − 1737028801.100000 = 20.000000` seconds. The decoded HTTP rows 8 and 12 instead differ by **19.980000** seconds; that is their decode-row gap, **not** the first-byte request-start gap. `independent-pcap-report.json` checks the selected frames and interval arithmetic separately from the builder. Do not combine timestamps from different collectors without checking their clocks.
- For the on-screen shortcut, show **only accepted frames from one series**. Apply `frame.number == 3 || frame.number == 20 || frame.number == 24` for the fixture's connection attempts, or `frame.number == 7 || frame.number == 12` for its request first bytes. Both exact accepted-only filters appear in `native-10-filter-03.png` and `native-10-filter-04.png`; use your own retained frame numbers for another capture. Choose **View > Time Display Format > Seconds Since Previous Displayed Packet**. The reviewed `native-accepted-3-delta-menu.png` and `native-accepted-3-delta-applied.png` show 0.000000, 60.000000 and 60.000000 on the three displayed SYN rows; `native-accepted-4-delta-menu.png` and `native-accepted-4-delta-applied.png` show 0.000000 and 20.000000 on the first-byte rows. A first displayed row's 0.000000 is **not** an interval from an earlier accepted event. Check that every later row's immediately preceding visible row is an accepted start of the same type, client and peer. **Seconds Since Previous Captured Packet** instead uses a potentially hidden capture predecessor and is not this shortcut.
- Check time references before trusting any displayed-row gap. Select a packet and use **Edit > Set/Unset Time Reference**, or that named packet-list context action, to inspect the reference marker; unset it afterward and recheck the filtered list. In the approved test, the **already accepted** frame 3 displayed `*REF*` when set, frames 20 and 24 still displayed 60.000000, and unsetting frame 3 restored 0.000000, 60.000000 and 60.000000 (`native-accepted-3-time-reference-set.png` and `native-accepted-3-time-reference-unset.png`). That test does **not** show what happens with an unrelated reference packet hidden by a filter. A reference-marked row is not a check-in merely because it appears; if an unaccepted reference or any extra row intervenes, abandon the shortcut for that pair and use the recorded epochs. The lecture warns that reference rows may remain visible despite a filter; verify the actual visible rows rather than assuming the filter removed them. The new checked example sets response frame 10 as a reference, then requests accepted rows 3, 20 and 24: row 10 remains visible and frame 20 displays 58.940000 from that response. Unsetting reference 10 restores accepted-only rows and the two 60.000000 gaps. These four actual `native-gap-*` views are separate from the older in-filter frame-3 control test; cite the appropriate test.
