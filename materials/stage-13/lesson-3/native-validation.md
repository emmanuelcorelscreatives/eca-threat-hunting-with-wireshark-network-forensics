## Reproduce the native inspection on an authorized offline file

1. **Identify the source before interpretation.** Record file location, authorization, SHA-256, collector/capture point and the record supporting that description. For this supplied synthetic PCAP, a read-only integrity check from the directory containing it is:

   ```sh
   printf '%s  %s\n' '741a40d9c1d1d3e3361b2bc4a670b9a5cd7d2e3b1e9d60d215d356b6e9417eb4' 'practice.pcap' | sha256sum -c -
   ```

   Stop if it fails. For **your own** authorized file, calculate and record its actual SHA-256; do not assign the synthetic digest to it. Open the file with **File → Open**, leaving the read filter empty unless the analysis explicitly requires and records one. Do not start a live capture. Record the packet-list display filter separately from any graph or Statistics filter.

2. Open **Statistics → Capture File Properties**. Record the first and last captured timestamps, their calculated difference, file timestamp precision, any reported drops, and every **Unknown** collector field. Consult the actual collection record for observation-point details, coverage and drop logs; a first-to-last packet window is not evidence of continuous collection. In this particular native build, do not substitute the displayed **2,362-byte Length** for the **2,378-byte physical file** or the **1,826 frame bytes**.

3. For comparable absolute times, choose **View → Time Display Format → UTC Date and Time of Day**. Verify the filled radio dot beside that format and verify the Time column afterwards. **Automatic (from capture file)** is a separate timestamp-*precision* choice; selecting or seeing it does not select UTC. Capture precision here is microseconds even when a text export prints nine decimal places. If you instead use **View → Time Display Format → Seconds Since Previous Displayed Packet**, first make sure *every displayed packet is a comparable accepted event*; the approved SYN filter alone does **not** meet that condition because it includes frame **1** and repeated frame **19**. Otherwise, subtract recorded accepted UTC start times. The approved `native-final-05-checked-time-format.png` establishes the selected previous-displayed time setting. `native-final-04-regular-accepted-deltas.png`, `native-final-04-variable-accepted-deltas.png` and `native-final-04-gap-accepted-deltas.png` establish the separately filtered accepted series and deltas **0/10/10**, **0/6/14** and **0/10/30 seconds**. They do not approve using deltas between every packet in the generic SYN filter.

4. Open **Statistics → Conversations**; select the **TCP** tab deliberately, record whether **Limit to display filter** and **Absolute start time** are checked, and note each relevant four-tuple, start and duration. The approved view leaves both unchecked, so start values are **relative to the first captured frame**. If inspecting **Statistics → Endpoints**, select and document a tab explicitly: the approved default screenshot shows **Ethernet**, not an IPv4 result. Neither a conversation nor an endpoint aggregate counts application check-ins.

5. Open **Statistics → I/O Graphs**. Write down each enabled row's exact display filter, interval, time reference, and Y Axis units before interpreting a peak or quiet bin. The approved state is the **unfiltered All Packets, 1 sec, relative-time** graph described above; the `tcp.analysis.flags` row is separate. Return to original numbered frames and their times to check which events fall in a chosen bin. `one-second-frame-bin-arithmetic.json` supplies a **raw-record calculation**, not a GUI measurement: using the first packet at **12:00:02 UTC** as relative origin, bin **8** spans 12:00:10–12:00:11 and contains frames **6, 7**; bin **20** spans 12:00:22–12:00:23 and contains frame **18**; bin **21** spans 12:00:23–12:00:24 and contains repeat frame **19**; bin **50** spans 12:00:52–12:00:53 and contains frames **26, 27**. The new native-final graph views establish bin 8 as two packets with representative frame 7, and bin 21 as one packet with representative frame 19; separate native packet-list views show the corresponding original frames. The original raw arithmetic remains a separate calculation. The supplied `native-final-02-graph-changed-10sec.png` also establishes the unfiltered 10-second state. If you choose a different interval or a new graph filter, record and verify that new state rather than extending the supplied approval.

6. Return to the frame list and apply `tcp.flags.syn == 1 && tcp.flags.ack == 0` in the **display-filter** bar to find *candidate* new connection attempts. Check the client and scoped peer **port**, original frame, raw sequence, source port, replies, and nearby retransmissions. On this file, frames **18** and **19** share source port **43102**, peer `203.0.113.30:8080`, and raw sequence **3200**: count **18** once, not **19** again. Clear the display filter to examine surrounding frames and the persistent four-tuple. For visible application starts, inspect request bytes or decoded requests separately; transport keep-alive-shaped, zero-payload packets are not application requests. Do not infer unseen requests from a long conversation.

## Fields to keep with each timing worksheet

Complete the fields below **separately for synthetic practice and for each of three future assessments in your own authorized capture**. **Record the capture SHA-256 explicitly** so that another analyst can identify the exact source. Do not fill an authorized-case row with the synthetic answer key.

- **Pass and source:** synthetic practice or authorized case; actual PCAP filename and path; **capture SHA-256**; analyst/date; basis of authority to inspect; original frame-number namespace.
- **Collection and window:** capture point and source of that description; first and last captured **UTC** timestamps and original frame numbers; calculated first-to-last duration; timestamp precision; coverage and drops **with sources**, or **unknown**; relevant capture-edge limits.
- **Scoped event:** local host **address and source port(s)**; peer **address and destination port**; direction; chosen comparable event, either distinct connection-attempt starts or visible application-request starts; how retries are excluded. Do not mix event types within an interval series.
- **Reproduction:** exact frame-list display filter; any separate Conversations limitation and graph-row filter; UTC format or other time reference; graph interval and units; bin boundaries and the **original frames actually inspected**; whether a previous-displayed-packet delta had only comparable displayed events.
- **Three assessments:** for each regular, variable, or apparently interrupted candidate, list accepted **original frame → UTC start time** pairs, successive subtractions and number of measured intervals; checked replies/retries and any transport trouble; whether enough cycles were captured; relevant scheduling and collection alternatives and the evidence **actually available**. State what is observed, calculated, and inferred separately.
- **Persistent session, separately:** four-tuple; first/last original frames, UTC times and observed span; visible application-request frames and bytes or method/URI if observable; transport-only probe frames and supporting fields; count of **successive comparable application-request intervals**; visible response or its absence; what hidden activity remains unknown.
- **Decision and next record:** confidence limit, including unavailable coverage or host context; smallest collector-health record for a possible observation gap, or task schedule / endpoint process-network record for a purpose question. If a needed record or authorized file is unavailable, write **unknown** or **authorized-case assessment pending**, not ‘zero drops,’ ‘skipped contact,’ deliberate jitter, network loss, or a command-and-control finding.
